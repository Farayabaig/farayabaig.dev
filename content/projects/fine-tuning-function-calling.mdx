## The problem

A multi agent platform lives or dies on tool calls. A model that returns almost valid JSON, picks the wrong function or invents an argument breaks the whole chain. Evaluating off the shelf models across domain specific tasks showed exactly **where they fell short on structured tool calls**.

## Open source: function calling SFT on Qwen2.5 3B

The core experiment is public, with [checkpoints on Hugging Face](https://huggingface.co/faraya1/Qwen2.5-3B-RAG-API-Finetuned-Models). I fine tuned a 4 bit Qwen2.5 3B with LoRA on **10,000 examples** from Salesforce's public xLAM function calling dataset, on a single free Colab T4, then scored it on **200 held out examples** it never saw in training.

The scoring is deliberately strict: inventing a tool costs 0.2 and inventing an argument costs 0.1, and output that is not valid JSON scores below zero. In an agent, calling a tool that does not exist is worse than calling none, so the metric punishes it.

The remaining errors sit in **parameter values**, and most are near misses, like `"small"` where the API expects `"s"`.

## Open source: RAG prompt tuning with DSPy

The evaluation side of this work is public. I wrote [rag-prompt-tuning-DSPy](https://github.com/Genie-Experiments/rag-prompt-tuning-DSPy) to answer a practical question: **is an automatically optimized prompt actually better than one an engineer writes by hand?**

  caption="Same retriever, same model, three prompts, two kinds of score."

    { label: "Score", detail: "similarity minus a length penalty" },
    { label: "Hallucination check", detail: "UpTrain factual accuracy" }
  ]}
/>

- **Three strategies, head to head.** A standard RAG prompt, a hand written prompt with strict grounding rules, and a prompt compiled by DSPy's BootstrapFewShot optimizer.
- **A metric that rewards the right thing.** Semantic similarity to the reference answer, minus a penalty for long answers, so the optimizer can't win by rambling.
- **Hallucination checks on top.** Every answer is scored for factual accuracy with UpTrain, because similar wording is not the same as true.
- **Public and internal data.** The same benchmark runs on PubMedQA and on Confluence documentation, so results aren't tuned to one domain.
- **Full traceability.** Every prompt DSPy sends to the model is counted and logged, so you can see exactly what the optimizer tried.

## Open source: GRPO for cited RAG answers

Supervised fine tuning teaches a model what good answers look like. I also wanted to see how far **reinforcement learning** could push a small model, so I trained [Qwen2.5 3B with GRPO](https://github.com/Farayabaig/grpo-rag-citations-qwen3b) to answer RAG questions in a strict format and cite its source:

```text
<think> which document answers the question, and why </think>
<document id> 2 </document id>
<answer> the answer, grounded in document 2 </answer>
```

Instead of a learned reward model, I wrote **four small rule based rewards**, which kept training cheap enough for a single free Colab T4:

- **Right document:** credit for citing the correct document ID, plus a bonus when the answer is grounded in that document's text.
- **Tags present:** partial credit for each of the three blocks.
- **No extra text:** nothing outside the three blocks.
- **Right order:** think, then cite, then answer.

Splitting format and correctness into separate rewards gives the model credit for what it got right instead of an all or nothing score.

**What it showed:** the model learned the format and kept it, with **99% format compliance** across the logged run. Citing the right, well grounded document held steady at about **0.55 out of 1**, which points to the next step: a softer document reward and a proper before and after evaluation on held out data.

## Key engineering decisions

<Decision title="Small models, tuned for the job">
A 3B or 7B model that reliably does one job is cheaper and faster to serve than a large general model. Tuning **Qwen 2.5 3B and Mistral 7B** gave the platform models built for the function calls it actually needed.
</Decision>

<Decision title="Evaluation before training">
Measuring off the shelf behaviour first meant the fine tuning targeted real failure modes rather than guesses, and gave a baseline to prove improvement against.
</Decision>

<Decision title="DSPy instead of manual prompt tweaking">
A systematic DSPy evaluation and prompt optimization workflow made progress **measurable and repeatable**, improving retrieval quality and response grounding without manual trial and error.
</Decision>

## Results

- A 3B model that returns valid tool calls 100% of the time and picks the right tool **98.8%** of the time on held out examples.
- Smaller, cheaper models tuned to perform the function calling tasks the platform needed.
- A repeatable, evidence based path to better fine tuning results for the team.

## What I would do next

Score the base model with the same functions to show the exact before and after gain, extend the evaluation to the full test split and a second benchmark, and reduce parameter value errors with normalisation hints in tool descriptions.
