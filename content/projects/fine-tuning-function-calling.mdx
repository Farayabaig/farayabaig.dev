## The problem

A multi agent platform lives or dies on tool calls. A model that returns almost valid JSON, picks the wrong function or invents an argument breaks the whole chain. Evaluating off the shelf models across domain specific tasks showed exactly **where they fell short on structured tool calls**.

## Open source: RAG prompt tuning with DSPy

The evaluation side of this work is public. I wrote [rag-prompt-tuning-DSPy](https://github.com/Genie-Experiments/rag-prompt-tuning-DSPy) to answer a practical question: **is an automatically optimized prompt actually better than one an engineer writes by hand?**

<Flow
  caption="Same retriever, same model, three prompts, two kinds of score."
  steps={[
    { label: "Datasets", detail: "PubMedQA and internal Confluence docs" },
    { label: "RAG pipeline", detail: "Haystack, BM25 retrieval, GPT-4o" },
    { label: "3 prompts", detail: "standard, hand written, DSPy optimized" },
    { label: "Score", detail: "similarity minus a length penalty" },
    { label: "Hallucination check", detail: "UpTrain factual accuracy" }
  ]}
/>

- **Three strategies, head to head.** A standard RAG prompt, a hand written prompt with strict grounding rules, and a prompt compiled by DSPy's BootstrapFewShot optimizer.
- **A metric that rewards the right thing.** Semantic similarity to the reference answer, minus a penalty for long answers, so the optimizer can't win by rambling.
- **Hallucination checks on top.** Every answer is scored for factual accuracy with UpTrain, because similar wording is not the same as true.
- **Public and internal data.** The same benchmark runs on PubMedQA and on Confluence documentation, so results aren't tuned to one domain.
- **Full traceability.** Every prompt DSPy sends to the model is counted and logged, so you can see exactly what the optimizer tried.

<Callout>The fine tuning code and data are private client work; the DSPy evaluation framework above is open source.</Callout>

## Key engineering decisions

<Decision title="Small models, tuned for the job">
A 3B or 7B model that reliably does one job is cheaper and faster to serve than a large general model. Tuning **Qwen 2.5 3B and Mistral 7B** gave the platform models built for the function calls it actually needed.
</Decision>

<Decision title="Evaluation before training">
Measuring off the shelf behaviour first meant the fine tuning targeted real failure modes rather than guesses, and gave a baseline to prove improvement against.
</Decision>

<Decision title="DSPy instead of manual prompt tweaking">
A systematic DSPy evaluation and prompt optimization workflow made progress **measurable and repeatable**, improving retrieval quality and response grounding without manual trial and error.
</Decision>

## Results

- Smaller, cheaper models tuned to perform the function calling tasks the platform needed.
- A repeatable, evidence based path to better fine tuning results for the team.
